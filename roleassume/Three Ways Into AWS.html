The picture on this page

Think of each AWS account as a building. A pipeline run is a visitor who needs a badge to get in. Here is every piece of the picture, with its real name underneath.

  • BuildingOne AWS account, for example the prd network account.Real name: AWS account
  • Head officeThe company’s main account, which runs all the others.Real name: IMS Root (AWS calls it the management account)
  • Signed noteProof from GitHub, made fresh for each run, saying which repo and branch the run comes from.Real name: OIDC token
  • BadgeWhat the pipeline becomes inside a building.Real name: IAM role
  • Master keyControl Tower’s own badge. It opens every room in every building.Real name: AWSControlTowerExecution
  • Guest listWho may get a badge. Each badge has its own list.Real name: trust policy
  • RoomsWhat a badge lets you do inside the building.Real name: permissions
  • Building rulesCompany-wide safety rules that apply to everyone inside, whatever their badge.Real name: guardrails (SCPs)
  • Reception passWay 3’s first badge, at head office. It is only good for one swap.Real name: the iamr role in IMS Root

What all three get right

All three ways start the same way, and it’s the most important part. GitHub gives each run a signed note. AWS checks the note and hands over a temporary badge that expires on its own. No password or key is stored anywhere.

What AWS says

  1. GitHub Actions is one of these: a pipeline service that runs outside AWS.
  2. This is the swap all three ways make: GitHub’s signed note (a “JSON web token”) in, a temporary badge out.
  3. So all three ways already follow AWS’s first and most important rule. The differences are in what happens next.

Way 1 · used by the old pipelines

Old secrets: straight to the master key

In one line: a secret in GitHub names Control Tower’s master key, and the run gets it in one step.

    What AWS says

    1. AWS wants the building rules to cover every badge in every account. “Principals” here means badges and users.
    1. One of Control Tower’s building rules. “Deny” means block.
    2. What it blocks: adding or changing CloudFormation extensions. Other rules block other things.
    3. Where: everywhere in the account.
    4. Who: only callers whose badge is not like…
    5. …the master key. So the master key is let through.
    6. The same exception is written into other Control Tower rules on this AWS page. It is there so Control Tower’s own work isn’t blocked. Open the AWS page ↗
    1. The master key was made by Control Tower. Adding GitHub to its guest list is a change to it.
    2. What can happen: repair work on the whole Control Tower setup, and compliance reports that are wrong.

    What it means for you

    • Risk: anyone who can run a pipeline in any tescoims repo could get the master key to the prd network account.
    • Risk: the building rules don’t stop the master key, so a pipeline mistake isn’t caught by them.
    • Future: none. Once every pipeline has moved, take GitHub off the master key’s guest list and delete the old secrets.

    Way 2 · used by the WS2 DNS pipelines

    WS2 list: straight to whatever badge it names

    In one line: one secret holds a list of badges, and the run gets the one for its account in one step, like Way 1.

      What it means for you

      • First: run the checker, find-deploy-role-arns.yml. It shows which badge each account in the list uses.
      • If it’s the master key: the same risks as Way 1.
      • If it’s a pipeline badge: fine for now. Still move it to Way 3 later, so all your pipelines follow the client’s one standard.

      Way 3 · used by your converted pipelines

      New IMS sign-in: reception first, then a pipeline badge

      In one line: the run gets a reception pass at head office, then swaps it for a badge made for pipelines.

        What AWS says

        1. Step one: GitHub’s note gets a pass in one central account. In Way 3, that’s IMS Root.
        2. Step two: the pass is swapped for a badge in each target account. The same two steps as Way 3.
        3. And the target badges get only what they need. Way 3’s badges are full admin.
        1. “Role chaining” is AWS’s name for Way 3’s swap: one badge used to get another.
        2. So after the swap a run has at most 1 hour of access. Long jobs need to finish their AWS work within it.

        What it means for you

        • Good: badges made for pipelines, the building rules apply, nothing is stored in GitHub, and the client controls every guest list in one place.
        • Watch: 1 hour of access after the swap, and it can’t be raised.
        • Watch: 14 of your accounts have no pipeline badge yet. Way 3 can’t reach them until the client creates one.
        • Watch: the badges are full admin, and outside the prd network the guest lists let in any repo in the 13 GitHub orgs.
        • Watch: the reception desk is in head office. That’s the one thing AWS’s advice would change.

        AWS’s advice

        What AWS recommends

        In one line: keep Way 3’s two steps, and fix three things.

        AWS doesn’t insist on one step or two. Its own GitHub example uses two steps, like Way 3. What its pages ask for is where the reception desk sits, how exact the guest lists are, and how many rooms each badge opens.

          Change 1 · Reception outside head office

          1. The management account is head office, IMS Root. Letting pipelines in is not a job only head office can do.
          2. SCPs are the building rules. They don’t reach anything in head office, reception passes included.
          1. That’s you: your pipelines run in GitHub, outside AWS.
          2. So AWS doesn’t insist on special pipeline accounts for you.
          3. But you do have to plan how the pipelines get in. That’s what this page compares.
          4. So AWS’s pages don’t name one account for the reception desk. They are clear about one thing: not head office.

          Change 2 · Guest lists with exact names

          1. A guest list must say who may come in, so other people’s repos can’t get a badge.
          2. The check decides which pipelines can get the badge. GitHub’s page shows one that lets in a single repo, and only its production environment: repo:octo-org/octo-repo:environment:prod.
          1. In plain words: a guest list can now check more details in GitHub’s note, such as the repo’s permanent ID and the environment.
          2. Your company’s GitHub signs its notes as tescoims.ghe.com. Ask the client’s architect to confirm this works for it before relying on it.

          Change 3 · Only the rooms each badge needs

          1. Give each badge only the rooms its pipeline needs.
          2. Starting broad is fine if you narrow it over time. Today’s pipeline badges are full admin.

          A one-step setup, with a proper pipeline badge in each account, is also standard practice. For your company the client’s standard is Way 3, so the advice is to keep it and make these three changes.

          What to do next

          1. Run the checker, find-deploy-role-arns.yml, to see which badge Way 2 uses.
          2. Ask the client to create pipeline badges (iamr roles) for the 14 accounts that only have the master key today.
          3. Ask the client to make the guest lists name exact repos, and the production environment for production badges. This is the follow-up already planned after the July sign-in incident.
          4. Raise the head office point with the client’s architect. Moving the reception desk is their design decision, and a longer-term change.
          5. Once nothing uses the master key, take GitHub off its guest list and delete the old secrets.
