How the pipeline gets into AWS

Your pipeline runs on GitHub’s computers, but the work happens inside your AWS accounts. To get in, it has to pick up a role: a set of permissions, a bit like an ID badge. This page uses your real code to show which badge the old pipeline used, which one the new pipeline uses, and why your client asked for the change.

The short version

Old pipeline

  • Went straight into the network account.
  • Used AWSControlTowerExecution: the master key that Control Tower, the system that runs your AWS organisation, keeps in every account for itself.
  • That key can do everything, and Control Tower’s safety rules make an exception for it.

New pipeline

  • Checks in first at IMS Root, the head office account.
  • Gets a badge there that is good for one thing only: swapping it for iamr-net-prd-deploy in the network account.
  • That badge was made for pipelines, and Control Tower’s safety rules apply to it.

Same pipeline, same Run workflow form, same Prepare → Drift check → Change set → Deploy boxes. Only the way in changed.

How GitHub OIDC works

OIDC lets a GitHub run sign in to AWS with nothing stored in GitHub: no password and no AWS keys. For every run, GitHub writes a short note and signs it. AWS checks the note, and if it matches what a role allows, hands back keys that stop working after an hour. Your old and new pipelines both sign in this way. What changed is which role the note opens.

The three pieces, and where each one is set up

In GitHub · your workflow file

Permission to ask for the note

id-token: write lets the run ask GitHub for a signed note. The configure-aws-credentials step then fetches the note and hands it to AWS, together with the role it wants (role-to-assume).

Where: latest_cft_deployment.yml, lines 62–63 and 176–181. GitHub runs the note service itself, at https://token.actions.tescoims.ghe.com. There is nothing else to set up in GitHub, and no secret.

In AWS · once per account

The identity provider

Tells the account which GitHub to believe: its address, and the audience GitHub writes on its notes (sts.amazonaws.com). AWS uses it to check that GitHub really signed the note.

Where: IAM → Identity providers → token.actions.tescoims.ghe.com, in IMS Root (390403857119). It isn’t in iam-roles-template.yml, so it was set up separately. The old way needs one in every account it signs in to; the new way only in IMS Root.

In AWS · one per job

The role

Its trust policy says which repos and branches may sign in with a note. Its permissions say what the run may do once it is in.

Where: IAM → Roles → iamr-net-prd-deploy → the Trust relationships and Permissions tabs, in IMS Root. Written in plat-eng/AWS-Landing-Zone → cloudformation/ims-root/iam-roles/iam-roles-template.yml.

What a typical OIDC role looks like

The smallest complete set-up, written the way the client’s templates are (CloudFormation). The real roles follow the same pattern; they are in The roles up close.

  1. The identity provider
  2. GitHub’s note service. AWS gets GitHub’s public signing keys from this address, to check signatures.
  3. The audience AWS accepts on notes: sts.amazonaws.com, AWS’s sign-in service.
  4. The role
  5. How long the keys last: 1 hour here. AWS allows up to 12 hours, but only 1 hour after a swap.
  6. Who may sign in · trust policy
  7. Only notes the identity provider above can verify. The client’s roles name the IMS Root provider by its full address instead (arn:aws:iam::390403857119:oidc-provider/…).
  8. sts:AssumeRoleWithWebIdentity: sign in with a signed note instead of AWS keys.
  9. The note must be addressed to AWS…
  10. …and its sub must match. This example lets in only the main branch of AWS-Landing-Zone.
  11. What it can do · permissions
  12. Look-only here (ReadOnlyAccess). A real pipeline role gets what its job needs.
  13. An example only. An account can have just one identity provider per GitHub address, and IMS Root already has one, so the client’s template only adds roles.

What’s in the signed note

  1. iss: who wrote the note. It must match the identity provider’s address.
  2. aud: who the note is for. It must be an audience the identity provider accepts, and match the role’s aud condition.
  3. sub: the line trust policies check most. It says which repo, and which branch, environment or pull request.
  4. More facts about the run. The client’s roles don’t check these; they check only aud and sub.
How GitHub writes sub
When the job runs from…sub looks like
a branch (a push, or Run workflow)repo:plat-eng/AWS-Landing-Zone:ref:refs/heads/main
a job that uses an environmentrepo:plat-eng/AWS-Landing-Zone:environment:prod
a pull requestrepo:plat-eng/AWS-Landing-Zone:pull_request
a tagrepo:plat-eng/AWS-Landing-Zone:ref:refs/tags/v1.0

In a trust policy, * matches anything. repo:plat-eng/AWS-Landing-Zone:* lets in all four lines above; repo:tescoims/* lets in every repo of that organisation. The client’s ppe and tst roles also list each organisation as repo:<org>@*: GitHub writes sub differently for repos created since 15 July 2026, and that second form lets them in.

Your old pipeline already used OIDC. The client’s problem is not OIDC itself, but which role the note opened: Control Tower’s master key, in every account. The new pipeline uses OIDC the way the client set it up: one identity provider in IMS Root, and roles made for the job.

    What it can do · permissions

    1. One permissions policy: AdministratorAccess, the AWS managed policy meant for full administrators.
    2. No permissions boundary, so nothing caps what that policy allows.
    3. Inside AdministratorAccess
    4. "Action": "*": every action in every AWS service: create, change, delete and read.
    5. "Resource": "*": on everything in the account.

    Why Control Tower’s safety rules don’t stop it

    1. A safety rule (an SCP) is a list of things nobody may do. It applies to every role in the accounts it covers, even to full administrators.
    2. This one: nobody may switch off or change AWS Config, the service that records every setting change in the account…
    3. …unless they are AWSControlTowerExecution. All of Control Tower’s mandatory blocking rules carry this exception, so that Control Tower can manage its own set-up. A pipeline holding this key can do the same: change or switch off Control Tower’s own logs, records, alerts and roles.
    4. This rule (GRCONFIGENABLED) is copied from the AWS Control Tower documentation. Your organisation may have more rules of its own.
