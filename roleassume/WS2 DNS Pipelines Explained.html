WS2 DNS Pipelines Explained

Route 53 · DNS records kept in Git

Your WS2 DNS pipelines, explained

Two pipelines keep the DNS records of your Route 53 zones in Git. Export copies a zone’s live records into a JSON file and opens a pull request. Apply compares that file with the live zone and makes the zone match. This page walks through both with the real code, and answers how they get into AWS.

Old way or new way? The old way. Every box that talks to AWS takes a role ARN for the account from the secret DEPLOY_ROLE_ARNS_JSON and signs straight in to that account in one step. Nothing goes through IMS Root. The files don’t say which role the secret holds; the checker below shows it.

The two pipelines at a glance

Pipeline 1

Export

ws2-dns-records-export.yml · in Actions: WS2 - DNS Records Export (batch)

  • Reads the live records of one zone, or of every zone in an account.
  • Writes one JSON file per zone, and opens a pull request with them.
  • Changes nothing in AWS.
  • Exporting every zone needs approval, except in sandbox.

Pipeline 2

Apply

ws2-dns-records-apply.yml · in Actions: WS2 -- DNS Records Apply (Gated / Audited)

  • Compares one zone’s JSON file with the live zone and makes the zone match.
  • Always previews first; changes only when you tick execute_changes.
  • Deletes records only when you also tick with_deletes.
  • Real changes need approval, except in sandbox.

Words on this page

hosted zone
Route 53’s container for one domain’s DNS records, for example example.com. A public zone answers the internet; a private zone answers only inside chosen VPCs.
DNS record
One entry in a zone: A (an IPv4 address), AAAA (IPv6), CNAME (another name), MX (mail), TXT (text, often for checks), NS (which name servers answer).
ALIAS
A Route 53 shortcut that points a name at an AWS resource, such as CloudFront or a load balancer. Export leaves these out.
stack_id
The pipelines’ name for a zone, and the name of its file: dns-records- plus the zone name with dots as dashes, for example dns-records-example-com.
hosted zone ID
Route 53’s own ID for a zone, starting with Z, like the form’s example Z060943926KMOQ012KNSW.
split-horizon
A public zone and a private zone with the same name. Export gives their files -public and -private endings.
config file
config/accounts/<account>/networking/<stack_id>.json: one zone’s records as JSON, kept in Git.
accounts registry
config/_accounts-registry.yaml: the list of account names both pipelines accept, such as network-prod and sandbox.
environment · approval
A GitHub setting that can make a job wait for a named reviewer. These pipelines wait on production; Apply in sandbox uses dns-records-sandbox.
change batch · UPSERT · DELETE
How Route 53 takes changes: one batch of actions, where UPSERT creates or updates a record and DELETE removes one.
preview
Working out and printing the changes without making them. Apply always previews first.
matrix
One job run several times, once per item in a list. Here, once per zone.
artifact
A file a run keeps: the zone list passed between boxes (kept a day), and the exported JSON files (kept 30 days).
sandbox
The test account. It never waits for approval, so changes are tried there first; the pipelines call it the canary.

How they get into AWS

Both pipelines use the same two steps, in every box that talks to AWS. First a script looks up the role for your account in the secret DEPLOY_ROLE_ARNS_JSON; then the ready-made AWS step signs straight in to that role. That is one hop, directly into the target account, with no IMS Root in between: the old way.

  1. Step one, in every box that talks to AWS: look up the role.
  2. The secret DEPLOY_ROLE_ARNS_JSON: one secret holding a list of role ARNs, one per account name (its shape is below).
  3. Picks the ARN for the account you typed…
  4. …and stops if there isn’t one.
  5. Hides the ARN in the log.
  6. Step two: the ready-made AWS step. It asks GitHub for a signed note about the run…
  7. …and uses it to sign straight in to that role, in the target account. One hop.
  8. The region the AWS commands go to. Route 53 itself is global.
  9. This copy is from Export’s List zones box (lines 219–237). The same two steps are in five more places.

Which roles does the secret hold?

GitHub won’t show the secret, but find-deploy-role-arns.yml (sent with this page) will show each entry’s account number and role name, the same way find-secret-roles.yml did for the other pipelines. Add it on a new branch in the repo where the WS2 pipelines run; the commit starts it, and the table is on the run’s Summary page. If an entry shows AWSControlTowerExecution, these pipelines use Control Tower’s master key too, with the same problems as your other pipelines had: its guardrails don’t apply to that role, and the GitHub trust added to it is drift.

Moving them to the new way

  1. Run the checker, so you know which accounts and roles are involved.
  2. The client creates an iamr role for each of those accounts, with its reception copy in IMS Root, that accepts the repo these pipelines run in. (Today the prd network roles accept only AWS-Landing-Zone and ims-app-identity.)
  3. In the six places above, replace the two steps with a lookup of the role name and the two sign-in steps your converted pipelines use: IMS Root first, then the swap with role-chaining: true and no session tags.
  4. Delete DEPLOY_ROLE_ARNS_JSON once nothing uses it.

Pipeline 1

Export

Export reads the live records of a zone (or of every zone in an account) and turns them into JSON files in Git. It changes nothing in AWS. The point is to get the current records into a file you can review and edit, so the next change goes through a pull request instead of the console.

How to run it

  1. Open the repo’s Actions tab and pick WS2 - DNS Records Export (batch).
  2. Click Run workflow, type the account, and name the zone (below). Leave the zone empty to export every zone.
  3. Click the green Run workflow. For every zone in an account other than sandbox, a reviewer of production has to approve.
  4. When it finishes, open the pull request it made, or download the files from the run page.

hosted_zone_idOptional. The zone’s ID. If you fill in both, they must name the same zoneZ060943926KMOQ012KNSW

    1. The first box. It doesn’t use AWS.
    2. Copies the repo, to read the registry.
    3. The account name must be in config/_accounts-registry.yaml…
    4. …otherwise it lists the valid names and stops.
    5. Reads the account’s environment and OU from the registry, for the log.

    Box 2 · Resolve filter logic

    1. The second box. It works out which zone, or zones, to export.
    2. It may ask GitHub for a signed note; it only needs one to look up a zone ID.
    3. The rule: a stack_id wins over a zone ID, and with neither, everything is exported.
    4. Spaces pasted into the form are stripped first; they would otherwise break every lookup.
    5. Both given? They must name the same zone, or the run stops.
    6. A stack_id alone (or a zone name, or the stack that created the zone): one zone.
    7. A zone ID alone: it asks Route 53 for the zone’s name…
    8. …and turns it into a stack_id: dns-records- plus the name with dots as dashes.

    1. The third box.
    2. Its own permissions: read the repo, and ask for a signed note. A list here replaces GitHub’s defaults, which is why contents: read is spelled out.
    3. Lists every hosted zone in the account, public and private.
    4. Each zone’s stack_id: dns-records- plus the zone name with dots as dashes.
    5. Two zones with the same name (split-horizon) get -public and -private endings…
    6. …and if that still clashes, the end of the zone ID, so no zone is ever dropped.
    7. One zone wanted: first the stack_id as given…
    8. …and as a last resort, the name of the CloudFormation stack that created the zone, through that stack’s HostedZoneId output.
    9. All mode: every zone.
    10. The chosen zones become a list of stack_id, zone name and zone ID…
    11. …saved to a file…
    12. …and passed to the Export box as an artifact, kept for one day.

    Box 4 · Gatekeeper approval

    1. The fourth box.
    2. Only for all zones, in an account other than sandbox. Exporting one zone never waits.
    3. environment: production: GitHub holds the run here until a reviewer of that environment approves it.
    4. What the reviewer is told: the account and how many zones.

    Box 5 · Export · when it runs

    1. The fifth box.
    2. always() makes GitHub check the conditions below, even though an earlier box may have been skipped…
    3. …so it runs when the approval passed or wasn’t needed.
    4. contents: write lets it push a branch…
    5. …and pull-requests: write lets it open a pull request.
    6. The whole history, needed to make a branch.
    7. Python for the export script. This is version 4 of the action, an old one; Apply uses version 5.
    8. Next come the two sign-in steps (lines 582–600).

    Box 5 · Export · check the sign-in

    1. Checks the sign-in worked by asking AWS “who am I?”…
    2. …and if it didn’t, lists the likely causes: the account isn’t in DEPLOY_ROLE_ARNS_JSON, the role doesn’t trust GitHub, or the role lacks permissions.
    3. Prints the account number it got into.

    Box 5 · Export · one JSON file per zone

    1. Fetches the zone list from List zones.
    2. No list, or an empty one: stop.
    3. Each zone becomes one file: config/accounts/<account>/networking/<stack_id>.json.
    4. pipeline/dns_records_export.py reads the zone’s live records and writes that file…
    5. …given the exact zone ID, so the private half of a split-horizon pair can’t be mixed up with the public half.
    6. Script OK and the file is there: exported.
    7. Script OK but no file: skipped (the zone wasn’t found or couldn’t be read).
    8. Script failed: failed, with its first error line as the reason.

    Box 5 · Export · the results

    1. Meant to print a table of the counts. These lines have no %s, so the numbers never appear and the labels run together on one line (see Things worth fixing).
    2. No zone processed: fail.
    3. No zone exported: fail, listing the skipped zones.
    4. At least one exported: success, followed by the list of files.

    Box 5 · Export · hand the files over

    1. Only when at least one zone was exported.
    2. Option A: the JSON files as a download on the run page…
    3. …kept for 30 days.
    4. Option B: a branch and a pull request.
    5. Uses the run’s own GitHub token to push and to open the pull request.
    6. The branch: feat/export-zone-<zone>-<account>-<date and time>, so every run gets a new one.
    7. Creates the branch…
    8. …commits the files. If nothing changed it makes an empty commit, so there is still a pull request to look at…
    9. …pushes it…
    10. …and opens a pull request into main.
    11. If GitHub refuses (for example when Actions isn’t allowed to create pull requests in this repo), it prints a link to open one by hand.
    12. Last, it writes the Summary page: the files, what gets exported, how to get the files, and what to run next.

    Pipeline 2

    Apply

    Apply takes one zone’s JSON file (the records you want) and compares it with the live zone in Route 53. It then sends Route 53 a change batch with the difference: UPSERT for records to add or change, and DELETE for records you removed from the file, if you allow deletes. The script that does this, pipeline/dns_records_apply.py, isn’t in the workflow file; the workflow runs it twice, once to preview and once to apply.

    Its safety switches

    Tick boxEmpty (the default)Ticked
    execute_changesPreview only; nothing changesPreview, approval, then the change batch
    with_deletesNo record is ever deletedRecords missing from the file are deleted

    Two more rules are built in. Every real change outside sandbox waits for a reviewer of production; sandbox goes straight on. And each run handles exactly one zone: with no stack_id or zone ID it stops, so there is no “all zones” for Apply.

    How to run it

    1. Merge the zone’s JSON file change into main first (the Export pull request, or your own edit).
    2. Actions tab → WS2 -- DNS Records Apply (Gated / Audited) → Run workflow, on main.
    3. Type the account, name the zone, and leave both tick boxes empty. Read the preview on the Summary page.
    4. Happy with it? Run again with execute_changes ticked (and with_deletes only if records should be deleted). Outside sandbox, a reviewer approves before anything changes.

      Things worth fixing

      Found while reading the two files. None of them stops the pipelines today, but the last two can make a run show or change the wrong thing.

      1. Export’s results table never shows its numbers (lines 712–716). The printf lines have no %s, so they print only the labels, run together. Use the same pattern as line 710, for example printf "%-50s %s\n" "[OK] Successfully exported" "$EXPORT_COUNT".
      2. Export uses an old version of setup-python (@v4, line 574). Apply already uses @v5.
      3. Apply’s header comment is out of date. It mentions a gate-dns-records environment and dry_run; the code uses production / dns-records-sandbox and execute_changes.
      4. A misleading name in Apply’s preview (line 384): DRY_RUN holds execute_changes, the opposite of what the name says. The summary prints it correctly.
      5. After opening the pull request, Export prints a “new pull request” link (line 895) rather than the pull request it just made.
      6. Split-horizon zones: Export names them …-public and …-private, but Apply’s lookup (lines 171–176 and 305) doesn’t. A …-private stack_id isn’t found, and a private zone’s ID turns into the plain name. Check how dns_records_apply.py picks the zone before using Apply on such a pair.
