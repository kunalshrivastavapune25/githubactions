Your New Pipelines Explained

Network accounts · CloudFormation and trust store pipelines

Your new pipelines, explained

You have two pipelines in GitHub Actions. One creates and updates CloudFormation stacks; the other keeps CloudFront’s trust store, the list of certificate authorities it accepts client certificates from, up to date. Both now get into AWS the new way, through IMS Root. This page walks through each one with the real code, from the button you press to what changes in AWS.

The two pipelines at a glance

Pipeline 1

CloudFormation deployment

latest_cft_deployment.yml · in Actions: CloudFormation Stack using S3 as required

  • Creates or updates one CloudFormation stack from a template in your repo.
  • You start it with Run workflow and pick the folder, stack, account, region and whether to deploy.
  • Four boxes: Prepare → Drift check → Change set → Deploy.
  • Safe by default: Deploy = no stops at the change set, a preview you review first.

Pipeline 2

Trust store

validate-trust-store.yaml · in Actions: Trust store

  • Checks the CA bundle (truststore.pem) for one environment and updates CloudFront’s trust store from it.
  • Starts by itself on a pull request (check only), or with Run workflow for tst, ppe or prd.
  • Three boxes: Validate → Compare with S3 → Apply.
  • Safe by default: Apply = no stops after showing what would change.

Both sign in the same way: GitHub → IMS Root → the network account, with no role names in GitHub secrets. Only the network accounts (prd, ppe and tst) can be picked, because only they have the new iamr roles so far.

Your YAML file is a workflow. Each box on the run page (Prepare, Validate…) is a job. Each - name: inside a job is a step.

One go of a workflow. Each run has a number (the run ID) and its own page with the boxes, the log of every step, and a Summary.
Run workflow
The button in the Actions tab that starts a pipeline by hand. It shows a short form; your answers are the workflow’s inputs.
runner
The fresh computer GitHub lends each box. It starts empty and is wiped afterwards, so every box copies the repo and signs in again.

The run’s overview page. Red errors, yellow warnings and notices appear at the top, and both pipelines write tables there.

A group of AWS resources created from one template and changed together.
template · params.json
The file that describes the resources (its name ends in -template.yaml), and the file with the values for its parameters.
change set
CloudFormation’s preview of exactly what would change. Nothing happens until someone executes it.
drift
A change made by hand in AWS that the template doesn’t know about.
trust store
CloudFront’s list of certificate authorities (CAs) whose client certificates it accepts, for sites that ask visitors for a certificate (mutual TLS).

The file with those CA certificates, one after another: text blocks that start with -----BEGIN CERTIFICATE-----.
pull request
A request to merge a branch into main. The trust store pipeline checks it by itself.

IMS Root · iamr roles
The head office account (390403857119) and the roles made for pipelines. Each box signs in there first, then swaps into the network account.

How both pipelines get into AWS

Every box that talks to AWS starts with the same two steps. GitHub writes a signed note for the run; the box shows it at IMS Root, the head office account, and gets the reception copy of a role; then it swaps that for the working copy in the network account. No password or role name is stored in GitHub. The companion page How the pipeline gets into AWS explains this in depth.

  1. Hop 1. A ready-made step from AWS. It asks GitHub for a signed note about this run and hands it to AWS…
  2. …asking for the reception copy of the role in IMS Root: the name the first box worked out.
  3. The session is named after the run number, so AWS’s activity log (CloudTrail) shows which run signed in.
  4. Hop 2. The same AWS step again…
  5. …role-chaining: true: use the role from hop 1 instead of asking GitHub again…
  6. …and swap it for the working copy in the network account.
  7. Everything the run does in the network account is logged under cft- and the run number.
  8. 3,600 seconds: one hour, the most AWS allows after a swap.
  9. No name tags on the swap: the working copy’s trust policy doesn’t allow them.
  10. The trust store pipeline uses the same two steps in its Compare and Apply boxes, with the session names truststore-compare-… and truststore-apply-… and the region from truststore.json.

Good to know

  • Every box signs in again. Each box runs on a fresh computer that is wiped afterwards, so nothing carries over except what an earlier box hands on (role names, file names).
  • The keys last one hour. That is why the CloudFormation Deploy box stops following a deployment after 55 minutes. The deployment itself carries on in AWS.
  • A trust store pull request never signs in. Only its Compare and Apply boxes are allowed to ask GitHub for a signed note, and they only run for Run workflow.
  • One exception: large CloudFormation templates are uploaded to S3 with the secret S3_ACCESS_GITHUB_ROLE, a separate role (S3-github-actions-oidc-role) in the shared services account.

Pipeline 1

CloudFormation deployment

This pipeline takes a CloudFormation template from your repo and creates the stack, or updates it if it already exists. It never changes anything blindly: it first checks that nobody changed the stack by hand, then makes a change set, a preview of exactly what would change. With Deploy = no it stops there for you to review; with Deploy = yes it executes the change set and follows it until CloudFormation finishes.

How to run it

  1. Put the template (a file ending in -template.yaml) and params.json in a folder under cloudformation/, and merge it to main.
  2. Open the repo’s Actions tab and pick CloudFormation Stack using S3 as required on the left.
  3. Click Run workflow, keep the branch on main, and fill in the form (below).
  4. Click the green Run workflow button. The run appears with a title like 📝 my-vpc · NETWORK · eu-west-1.
  5. Open it and watch the boxes: green = passed, red = failed, grey = skipped.
  6. Read the Summary: the plan, the drift check, the list of changes and a link to the change set in the AWS console. With Deploy = no, review it there and click Execute change set yourself, or run the pipeline again with Deploy = yes.

    🧰 Prepare · check the account and the stack

    1. Asks AWS “who am I?”…
    2. …and stops if it isn’t the account you picked. A safety net: the run never touches another account.
    3. Asks CloudFormation for the stack’s state.
    4. Not found (or only ever previewed): a new stack, so create.
    5. Exists and settled: update, after the drift check.
    6. Its first create failed, so it can’t be updated: delete it in the console and run again.
    7. Busy: something is changing it right now. Wait, then run again.
    8. Deploy yes or no, spelled out in the log.
    9. The 🧰 Prepare table on the Summary page…
    10. …including the role it signed in as, “via IMS Root”.

    🔎 Drift check

    1. 🔎 Drift check, the second box.
    2. Only for an existing stack. For a new stack this box is grey (skipped).
    3. Starts CloudFormation’s drift detection: every resource is compared with the template.
    4. Asks every 10 seconds until it is done.
    5. Drifted…
    6. …prints a table of the resources that changed and, for each changed property, what the template says and what AWS has now…
    7. …and stops before the change set: undo the change in AWS, or add it to the template, then run again.
    8. The box turns red, and Change set and Deploy don’t run.
    9. No drift: green, and the run carries on.
    10. If CloudFormation couldn’t check every resource, it says why, warns, and carries on.

    📝 Change set · when it runs

    1. 📝 Change set, the third box.
    2. Runs when Prepare passed and the drift check passed or was skipped, unless you cancelled the run.
    3. Hands on to Deploy: whether anything changes, the change set’s name and the stack’s ID.
    4. The files and the create-or-update decision from Prepare.

    📝 Change set · large templates go through S3

    1. Only for templates over 51,200 bytes.
    2. Signs in with a separate role kept in the secret S3_ACCESS_GITHUB_ROLE: S3-github-actions-oidc-role in the shared services account.
    3. A unique name for this run’s copy: the stack name and the time.
    4. presign.py makes two short-lived links: one to upload, one to read.
    5. Uploads the template with the upload link…
    6. …and passes the read link on to the next steps.
    7. Then the box signs in to the network account with the same two steps as Prepare.

    📝 Change set · check the template and the parameters

    1. The template comes from S3 (large) or straight from the file.
    2. CloudFormation reads the template and reports mistakes before anything is created.
    3. How each parameter gets its value, the same rules as aws cloudformation deploy:
    4. for an existing stack, it first reads which parameters the stack has now;
    5. a value in params.json is used;
    6. not in params.json but the stack has it: the stack keeps its current value.
    7. Values of hidden parameters (NoEcho, such as passwords) are blanked out in the log.
    8. A key in params.json that the template doesn’t have gets a warning and is ignored.

    📝 Change set · create it

    1. The change set’s name: gha-, the run number and the attempt.
    2. CREATE for a new stack, UPDATE for an existing one.
    3. Asks CloudFormation to work out the changes. Nothing in AWS changes yet.
    4. Allows templates that create IAM roles with fixed names.
    5. A description with the run number and who started it, visible in the console.
    6. Waits until CloudFormation has worked out the changes.
    7. Nothing would change: the box passes, and there is nothing to deploy…
    8. …so the empty change set is deleted.
    9. Any other problem: a red box with CloudFormation’s reason.

    📝 Change set · show what will change

    1. Counts the changes: added, modified, removed, replaced.
    2. One summary line in the log, then the list (example below).
    3. Replacements get a warning: the resource is deleted and created again.
    4. So do removals.
    5. Older change sets still waiting on this stack get a warning, so nobody executes the wrong one.
    6. A direct link to this change set in the AWS console.
    7. Deploy = yes: the Deploy box executes it next.
    8. Deploy = no: nothing is deployed. Review it in the console and execute it yourself.

    What the list means: ➕ add, 🔧 modify, ➖ remove, 🔄 replaced (deleted and created again). Under each resource, ~ lines show a property’s value before → after. The same list, plus a table, is on the Summary page.

    🚀 Deploy · execute and follow

    1. Runs only with Deploy = yes, when the Change set box passed and found something to change.
    2. The repo’s default branch (main), for the check below.
    3. Running from another branch gets a warning: you are deploying code that isn’t merged yet.
    4. Executes the change set: now AWS really changes.
    5. Follows the stack’s events every 15 seconds and prints each new one.
    6. Stops following after 55 minutes, because the sign-in lasts an hour…
    7. Each round it reads the stack’s state…
    8. …and it is finished when the stack is settled and the change set has been used.
    9. Still busy after 55 minutes: the box turns red, but the deployment is not cancelled. It carries on in AWS; follow it in the console.

    🚀 Deploy · the result

    1. Something else changed the stack first, so this change set was not used. Run the pipeline again.
    2. CREATE_COMPLETE or UPDATE_COMPLETE: success.
    3. The update failed, and CloudFormation put the stack back as it was.
    4. The first create failed. Delete the stack in the console before trying again.
    5. The update and the roll-back both failed: in the console use Stack actions → Continue update rollback.
    6. The create and the roll-back both failed: delete the stack, keeping any resources that block it.
    7. Success: a “Deployed” notice at the top of the run.
    8. Failure: a red error with the reason; the Summary page lists what failed and every stack event.

    Pipeline 2

    Trust store

    Some CloudFront sites use mutual TLS: the visitor’s system must show a certificate too, and CloudFront only accepts certificates issued by the certificate authorities (CAs) in its trust store. A trust store is built from one file, a CA bundle in S3. You keep that file in Git, one per environment, and this pipeline checks it, shows what would change, and puts it live.

    The files it works with

    1. account_id: the network account the trust store lives in. trust_store: its name, ID or ARN.
    2. bucket, key, region: where the trust store’s file is in S3. CloudFront doesn’t say which file a trust store was built from, so truststore.json ties the two together.
    3. This is how the top of the workflow describes truststore.json. Each environment folder has its own.

    How to run it

    1 · Check a change

    Pull request

    1. In a branch, edit truststore/<env>/truststore.pem: add or remove a CA certificate.
    2. Open a pull request to main.
    3. The check runs by itself (🧪 Trust store check · PR #…). Problems show on the file’s lines in the pull request; the summary lists the certificates added and removed.
    4. Merge when it is green. Nothing in AWS has changed yet.

    2 · Put it live

    Run workflow

    1. Actions tab → Trust store → Run workflow, on main.
    2. Pick the environment and leave Apply = no the first time.
    3. Read the Compare summary: certificates added, removed, replaced and unchanged.
    4. Run it again with Apply = yes. The summary shows the upload and the trust store becoming active; the previous file is kept as an artifact.

    Watch one run

    Pick the kind of run, then step through it.

      What the check looks for

      truststore_update.py holds the file to CloudFront’s rules for a trust store, plus a few of its own. The same checks run on a pull request, in Validate, and again before Apply.

      Errors: the file is refused

      • Only certificate blocks. Comments start with # and contain no -; no blank lines.
      • X.509 version 3 certificates, with RSA 2048, 3072 or 4096 keys or ECDSA P-256 or P-384 keys, signed with SHA-256, 384 or 512.
      • At most 25 certificates and 1 MB in total (CloudFront’s limits).
      • No private keys, no certificate requests (CSRs), no duplicates.
      • A certificate you add must be a CA certificate, not a client’s own certificate, and must not be expired.

      Warnings: flagged, but allowed

      • Problems with certificates that are already in the trust store.
      • Certificates that expire within 30 days.
      • Signs that the trust store doesn’t use the S3 file (for example, a different number of certificates).

      Before anything changes

      • AWS signed the run in to the account in truststore.json.
      • The trust store isn’t in the middle of another update.
      • Something actually changed. If not, there is nothing to apply.

      Changing or extending them

      • Add an account to the CloudFormation pipeline, once the client has made an iamr role for it: add its name to the roleAlias options (lines 36–39), and add a line like the ones in Pick the roles (lines 120–122) with the role name and the 12-digit account number.
      • Add an environment to the trust store pipeline: create truststore/<env>/ with truststore.pem and truststore.json, add it to the env options (lines 44–47), and add a line in Pick environment and role (lines 107–109).
      • Leave these as they are: role-chaining: true, role-skip-session-tagging: true and role-duration-seconds: 3600 in every second sign-in step, and id-token: write (the whole CloudFormation workflow; only Compare and Apply in the trust store one).
      • Large templates still use the S3_ACCESS_GITHUB_ROLE secret. If the client wants that to go through IMS Root as well, the S3 step needs the same two sign-in steps and an iamr role for the shared services account.
      • The drift-aware version of the CloudFormation pipeline (drift shown as information, and a change set that lists what it would undo) is still on the old sign-in. It needs the same conversion before it can replace this one.

      Before the first real runs

      1. Ask the client to confirm that iamr-net-prd-deploy and iamr-net-tst-deploy exist in network prd and tst. Only the ppe account’s file was shared.
      2. CloudFormation: run once on PPE-NETWORK with Deploy = no. The Prepare summary should say Signed in as iamr-net-ppe-deploy (via IMS Root).
      3. Trust store: run once for tst with Apply = no. Compare should list the certificates as unchanged, unless your file differs from S3.
      4. Then make a real change in tst and apply it, before doing the same in ppe and prd.
